# Seven Heaven · Rétrocollecte mensuelle automatisée

L'orchestrateur `tools/orchestrate_historical_bulk.py` s'appuie strictement sur `tools/import_historical_bulk.py` et la cohorte existante de **31 actifs historiquement qualifiés**. Aucun symbole n'est codé en dur par actif. Les autres identités du Top250 (dont HYPE, DOT et ASTER) NE sont PAS encore incluses dans cette première phase : le registre d'identité `top250-identity-evidence.json` poursuit sa qualification indépendamment. Une identité validée n'est pas automatiquement un mois complet de bougies.

Au premier lancement après fusion, l'orchestrateur interroge la liste des GitHub Releases déjà publiées, conserve le mois de septembre 2026 déjà archivé et sélectionne les **deux mois complets les plus récents manquants** : a priori août et juillet 2026. Les ZIP Binance Spot natifs `1m` sont vérifiés via leur `.CHECKSUM` officiel, identités CoinGecko préqualifiées, périodes UTC complètes et OHLCV. Chaque mois reçoit **une Release GitHub immuable** `crypto-spot-bulk-YYYY-MM-1m` comportant les ZIP originaux et le manifeste, sans les ajouter à l'historique Git. Même si certains actifs n'existaient pas ce mois, le manifeste expose `unavailable` par paire, sans les inventer. Le mode de lecture continue utilise la présence des tags publiés comme checkpoints ; il refuse d'écraser une Release existante et vérifie les noms des assets après l'envoi.

La collecte est programmée à **01:19, 07:19, 13:19 et 19:19 UTC** (4 fois/jour), **au maximum 2 mois par exécution**, avec une marge de 7 jours après la fin d'un mois pour éviter les ZIP non encore publiés par Binance. L'étendue de recherche descend prudemment jusqu'à janvier 2017 inclus, sans déclarer le « Max » atteint. Les exécutions GitHub Actions cron peuvent être retardées/ignorées : vérifier les runs et les Releases réellement créées. Un commit de code/workflow ordinaire ne doit pas amorcer une nouvelle collecte ; **seul l'ajout du fichier de permission** dans la fusion active le lancement initial. Les prochains runs ne modifient pas Trader/Administrator/Bridge, et ne recopient jamais les ZIP dans Git classique.

Le prochain chantier industriel après plusieurs mois effectivement archivés : faire absorber au même importateur les identités CoinGecko ↔ Binance Spot approuvées par `top250-identity-evidence.json`, en conservant les Releases déjà immuables et en prévoyant des **Releases complémentaires** pour les mois déjà couverts. Les actifs sans paire Binance Spot nécessitent un autre fournisseur, pas une correspondance inventée. Ce collecteur ne résout pas encore `Max` ou les 250 actifs.
