## 3. Recovery sequence that must be remembered

### 40.4.80 — rejected

The late Atlas hydration direction was a failure in real Firefox use. It created severe freezes / unusable interaction and interfered with Top 5 / core responsiveness.

Rule learned:

**Never solve Firefox pressure by making the critical Atlas cockpit appear late.**

Critical controls and the decision cockpit must exist immediately. Heavy internals may be demand-resident, but the operator shell cannot be delayed behind an expensive hydration wall.

### 40.4.66 — recovery base, not absolute gold

40.4.66 restored much of the responsiveness. It is a recovery reference, not an untouchable perfect build: the graph could still occasionally remain empty until operator reset.

### 40.4.81

### 40.4.82

Learning runtime moved closer to true demand. No Learning IndexedDB/reconciliation/collector work should happen until the Simulation/Learning path is actually opened.

### 40.4.83

Operator UI notes / Chronos / context ribbon work.

### 40.4.84

Aether Trust / status work, but an incorrect permanent second Aether row was introduced.

This build also introduced the important Section 04 ownership regression: Storage Health and Grey Plate were replaced by placeholders after the canonical runtime / Window Manager had already captured the real nodes.

### 40.4.86

### 40.4.87

Real Firefox evidence then showed Section 04 was broken, so the operational seal was revoked.

### 40.4.88

**40.4.88 is the current published authority at thread end.**

### D-11 — Shared runtime monolith

Status: `OPEN-HIGH-RISK`

The historical audit measured the main shared runtime at more than 52k lines / ~2.5 MB; the current first-click gate still explicitly exists because the shared runtime is around 3 MB and can finish parsing after the header becomes paintable.

This is a current structural risk:

- huge blast radius for small edits;
- high parse/compile cost;
- many historical event/timer/storage owners in one scope;
- high probability of distant regression from local surgery.

Do NOT perform a big-bang refactor.

Preferred policy:

- protect stable old code;
- route new features into explicit modules;
- retire one proven-dead owner at a time;
- only extract old code when boundaries and rebind behavior are demonstrably stable.

### D-13 — No-Ryzen / no-local-producer semantics

Status: `OPEN-HIGH-PRIORITY`

The local Ryzen producer is no longer available.

The current Atlas presentation/runtime still contains historical local-production language and controls, including Ryzen/Ollama/Bridge production expectations.

The final audit also identified a dangerous future mismatch: a non-Book machine can still fall into a local-production role and keep bounded Bridge supervision alive when the local producer does not exist.

New semantic target:

`LOCAL PRODUCER = NOT CONFIGURED / OFFLINE`

Then:

- Ryzen = OFFLINE;
- CPU = N/A;
- GPU = N/A;
- Ollama = N/A;
- local Atlas generation = unavailable;
- local Bridge = unavailable;
- no periodic Bridge/Ollama supervision while no producer is configured;
- historical Atlas reports/CURRENT/memory remain readable;
- Binance LIVE, Graph, Top 5, Oracle and public/read-only functionality remain available.

Do NOT report CPU/GPU as `0 %` because that falsely implies a live idle machine. Absence is `N/A / OFFLINE`.

This debt requires careful inspection of the actual large runtime owner before changing behavior. Do not patch from a partial source excerpt.

## 12. Final thread truth

The project is not “broken everywhere”. The main lesson of this thread is narrower and more useful:

**the application became large enough that duplicate presentation owners and post-bind DOM replacement are now more dangerous than the feature code itself.**

The safest next progress is therefore owner consolidation, not another broad performance wave.

Current stable direction:

- keep core market/graph/Top5/V7 hot;
- keep critical shells immediately present;
- make genuinely heavy secondary bodies true-lazy;
- one presentation owner per responsibility;
- never detach/replace a root behind Window Manager’s back;
- do not trust stale diagnostics as architectural authority;
- model absent local hardware as OFFLINE/N/A;
- prove non-regression before publishing.

This checkpoint is the final canonical handoff of the closing thread.
